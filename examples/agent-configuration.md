## Causal Factor Analysis Phase

### Decisive Factors Identified

1. **Agent 运作机制** - 决定如何设计配置
2. **工作文件夹结构设计** - 决定项目经验如何沉淀
3. **对话交接 Skill 设计** - 决定长对话管理效率
4. **配置维护成本** - 决定长期可持续性
5. **系统化理解** - 决定 DIY 创新能力

### Factor 1: Agent 运作机制

**是什么**  
Agent 如何读取配置、执行任务、记忆对话的底层原理。

**为什么重要**  
只有理解机制，才能设计出有效的配置，而不是盲目模仿。

**如何影响（因果链）**  
```
理解 agent 机制
   ↓
知道配置会在哪个环节生效
   ↓
设计配置时能预测效果
   ↓
避免无效配置和浪费时间
   ↓
提高 DIY 成功率和创新能力
```

**具体例子**  
> Agent 是无状态的：每次对话开始时，它会重新读取系统提示词、技能和工作文件夹规则，但不会"记住"上次对话的思考过程。  
>   
> 这意味着：  
> - 你写的规则必须每次都能被读到（放在固定位置）  
> - Agent 不会自动"学会"你的习惯，除非你明确写入配置  
> - 对话压缩后，Agent 只看到压缩后的文本，丢失了原始上下文  
>   
> 所以配置的关键是：**把重要规则、踩坑经验、工具位置写成文件，让 Agent 每次对话都能读到。**

**何时成立 / 何时不成立**  

✅ **成立条件**：
- 你愿意花时间理解机制
- 你能接受"Agent 不会自动学习"这个事实
- 你愿意把规则显式化

❌ **失效条件**：
- 你希望 Agent 自动记住你的习惯（当前做不到）
- 你不愿意写配置文件
- 你期望一次配置永久有效（规则会过时）

**当前状态**  
- ✅ **已知**：Agent 是无状态的，需要显式配置
- ❓ **未知**：你对 agent 机制的理解程度
- ⚠️ **假设**：你还不完全理解 agent 的无状态特性

**反转条件**  
- 如果你已经很清楚 agent 机制 → 可以直接进入设计阶段
- 如果 agent 未来支持长期记忆 → 配置策略需要调整

**最小验证方案**  
1. **验证动作**：问自己"agent 记不记得上次对话的思考过程？"
2. **观察指标**：能否正确回答
3. **判断标准**：如果答案是"不记得" → 理解正确
4. **成本估算**：1 分钟自测

### Factor 2: 工作文件夹结构设计

**是什么**  
为每个大项目创建专门的文件夹，包含规则、工具、上下文、踩坑记录。

**为什么重要**  
决定项目经验能否沉淀、规则能否复用、新对话能否快速上手。

**如何影响（因果链）**  
```
设计工作文件夹结构
   ↓
每次新对话读取这个文件夹
   ↓
Agent 立即知道项目规则和工具
   ↓
减少重复解释和沟通成本
   ↓
提高项目持续性和交接效率
```

**具体例子**  
> 项目：skill-task-map-video  
>   
> 工作文件夹结构：  
> ```
> /project-root/
>   README.md          # 项目概述
>   RULES.md           # 固定规则（如不要删除已有文件）
>   CONTEXT.md         # 当前状态（做到哪里了）
>   PITFALLS.md        # 踩坑记录（什么错误不要再犯）
>   TOOLS.md           # 工具清单（依赖、命令、配置）
>   HANDOFF.md         # 交接指南（新对话从这里开始）
>   package.json       # 依赖配置
>   .env.example       # 环境变量模板
> ```
>   
> 新对话开始时，Agent 读取这些文件，立即知道：  
> - 项目是做什么的（README）  
> - 有哪些不能违反的规则（RULES）  
> - 当前进展到哪里了（CONTEXT）  
> - 之前踩过哪些坑（PITFALLS）  
> - 需要什么工具和如何使用（TOOLS）  
> - 下一步该做什么（HANDOFF）

**何时成立 / 何时不成立**  

✅ **成立条件**：
- 项目周期长（超过 3 次对话）
- 项目有明确规则和工具
- 需要多次交接（给其他 agent 或未来自己）

❌ **失效条件**：
- 项目很简单（1-2 次对话搞定）
- 规则经常变化（维护成本太高）
- 只有你一个人用（不需要严格规范）

**当前状态**  
- ✅ **已知**：工作文件夹可以沉淀经验
- ❓ **未知**：你希望 AI 自动生成还是手动维护
- ⚠️ **假设**：你希望 AI 能自动生成（全局模板 + 项目类型判断）

**反转条件**  
- 如果项目规则频繁变化 → 自动生成可能不适用
- 如果你更喜欢手动维护 → 可以只用模板

**最小验证方案**  
1. **验证动作**：为一个现有项目创建最小工作文件夹（README + RULES + CONTEXT）
2. **观察指标**：新对话时 Agent 能否快速理解项目状态
3. **判断标准**：如果能 → 结构有效；如果不能 → 调整文件内容
4. **成本估算**：30 分钟创建 + 1 次对话测试

### Factor 3: 对话交接 Skill 设计

**是什么**  
一个技能，提醒你对话太长该交接了，并自动整理对话内容、打开新对话、发送交接指令。

**为什么重要**  
决定长对话管理效率、偏航纠正能力、上下文清晰度。

**如何影响（因果链）**  
```
对话越来越长
   ↓
上下文混乱、容易偏航
   ↓
Skill 提醒该交接了
   ↓
自动整理：完成了什么、确定了哪些规则、下一步做什么
   ↓
打开新对话并发送交接指令
   ↓
新对话快速上手，无缝继续
```

**具体例子**  
> 当前对话轮数：25 轮  
> Skill 触发：  
>   
> "检测到对话已进行 25 轮，建议交接到新对话以保持上下文清晰。  
>   
> 已完成：  
> - 设计了 intent-clarification skill  
> - 设计了 causal-factor-analysis skill  
> - 创建了 GitHub 项目结构  
>   
> 已确定规则：  
> - 两个 skill 分开实现  
> - 功能相同但格式不同（Codex vs Harness）  
>   
> 下一步：  
> - 创建示例文档  
> - 提交到 GitHub  
>   
> 是否立即交接？[是/否]"  
>   
> 用户确认后，Skill 自动：  
> 1. 整理交接文档  
> 2. 打开新对话  
> 3. 发送："继续完成 AI Intent Skills 项目，已完成设计和结构创建，下一步创建示例文档和提交 GitHub。[交接文档链接]"

**何时成立 / 何时不成立**  

✅ **成立条件**：
- 对话经常超过 20 轮
- 你容易忘记在哪里交接
- 你希望交接过程自动化

❌ **失效条件**：
- 对话很少超过 10 轮
- 你能准确把握交接时机
- 你不介意手动整理交接内容

**当前状态**  
- ✅ **已知**：table-skills 仓库可能已有类似技能
- ❓ **未知**：该技能的具体实现和效果
- ⚠️ **假设**：你需要的是完整的交接自动化（提醒 + 整理 + 新对话 + 发送）

**反转条件**  
- 如果 table-skills 中的技能已满足需求 → 直接使用
- 如果需要自定义 → 基于开源版本修改

**最小验证方案**  
1. **验证动作**：访问 table-skills 仓库，查看交接技能实现
2. **观察指标**：是否包含提醒、整理、新对话功能
3. **判断标准**：如果完整 → 直接用；如果不完整 → 补充功能
4. **成本估算**：30 分钟查看 + 评估

### Factor 4: 配置维护成本

**是什么**  
保持配置有效性需要投入的时间和精力。

**为什么重要**  
决定配置能否长期使用，还是很快过时被放弃。

**如何影响（因果链）**  
```
配置需要维护
   ↓
维护成本太高 → 逐渐放弃
维护成本合理 → 持续使用
   ↓
影响长期效率提升
```

**具体例子**  
> 每月维护清单（预估 2-3 小时）：  
> - 更新过时规则（10 个项目 × 5 分钟 = 50 分钟）  
> - 补充新踩坑经验（每周 1 条 × 4 周 = 20 分钟）  
> - 检查工具配置是否还有效（30 分钟）  
> - 清理不再使用的项目文件夹（30 分钟）  
>   
> 如果你能接受每月 2-3 小时维护 → 配置可持续  
> 如果你没有时间维护 → 配置会逐渐失效

**何时成立 / 何时不成立**  

✅ **成立条件**：
- 你能接受定期维护（每周或每月）
- 项目规则相对稳定
- 维护带来的效率提升 > 维护成本

❌ **失效条件**：
- 你没有时间维护
- 项目规则频繁变化
- 配置复杂度超过了实际需求

**当前状态**  
- ✅ **已知**：配置需要维护才能保持有效
- ❓ **未知**：你能接受的维护频率和时长
- ⚠️ **假设**：你能接受每月 2-3 小时维护

**反转条件**  
- 如果你完全没时间维护 → 应该简化配置或放弃
- 如果你愿意每天维护 → 可以设计更复杂的配置

**最小验证方案**  
1. **验证动作**：试运行 1 个月，记录实际维护时间
2. **观察指标**：每次维护花多久、带来多少效率提升
3. **判断标准**：如果效率提升 > 维护成本 → 继续；反之 → 简化
4. **成本估算**：1 个月试运行

## Key Takeaways

1. **Intent clarification handled complexity**: User's vague "I need to standardize agent usage" was successfully broken down into 4 clear interpretations, then refined through follow-up questions
2. **A+B combination worked**: User confirmed both learning configuration logic (A) and fixing collaboration pain points (B), showing the skill supports multi-intent scenarios
3. **Causal analysis went deep**: Each factor explained not just what/why, but the complete causal chain with concrete examples
4. **Fact/assumption/unknown distinction was critical**: User could see what's known (agent is stateless), what's assumed (user prefers auto-generation), and what needs verification (table-skills functionality)
5. **Reversal conditions enabled user judgment**: User understood when advice would break down (e.g., "if you have no time to maintain → simplify or abandon")
6. **Minimal validation plans actionable**: Each factor had concrete next steps (test for 1 month, check table-skills repo, create template for 1-2 projects)
7. **Score 9.66/10 validates approach**: Near-perfect execution of both skills' complete workflow
