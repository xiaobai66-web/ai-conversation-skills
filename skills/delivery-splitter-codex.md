# 交付分拣 Skill

这个 Skill 解决一个常见问题：聊天过程很长，模型最后把过程中的话一起交付了。

例如：

- 用户说“好看优先”，这是工作排序标准，不应原样出现在图片提示词里。
- 用户纠正了旧方向，纠正内容应该更新工作规格，不应该变成网页上的说明文字。
- 用户问“我还剩几个苹果”，答案要对准“我”，不要把“我们”的过程带进来。

## 什么时候使用

适用于：

- 经过多轮修改的答案、提示词、网页、报告、代码说明或其他成品
- 对话中出现旧版本、新版本、用户纠正、临时想法或多个方向
- 用户要求“只给最终结果”“不要解释过程”或交付内容会被别人直接看到

简单、明确的一问一答不必启动完整流程。

## 工作流程

交付前静默分成四类：

1. **交什么**：用户要的最终内容和格式。
2. **最后定了什么**：最新、明确、没有被撤回的要求。新决定覆盖旧决定。
3. **只属于过程的东西**：纠正、旧方向、临时方案、占位文字、误解说明和工作时的原话。
4. **成品里要出现什么**：交付物真正需要的事实、内容和可观察效果。

把优先级翻译成成品效果，不要复制优先级原话。例如把“好看优先”转成“脸部清晰、人物占主要面积、背景简洁”，而不是写成“用户要求好看优先”。

## 交付前检查

- 主体和范围是否正确（例如“我”与“我们”）？
- 是否使用了最后确认的方向？
- 格式、长度和媒介是否符合要求？
- 是否混入了用户纠正、旧版本、临时占位或内部工作话？
- 每一句是否都服务于最终交付？

如果存在会改变成品的关键歧义，只问一个最必要的问题；如果不会改变结果，就做最小合理假设并直接交付。

除非用户明确要求解释，否则只输出他要的答案或成品，不复述聊天过程、废弃版本或模型曾经的误解。

## 快速例子

- “我有一个苹果……我吃掉了一个，我还剩几个？” → `0 个苹果`
- “好看优先”的图片任务 → 输出具体的构图、主体、灯光和背景要求，不把“好看优先”当作画面文字。
